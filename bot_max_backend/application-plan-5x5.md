# Логика подборки программ и плана 5×5

Документ описывает, как backend считает персональный результат по каждой программе, как
формирует «Рекомендации по направлению» и как собирает план из 5 вузов и 5 программ.

Все правила вынесены в чистые классы без Spring и БД, поэтому их можно тестировать и менять
независимо от остального приложения.

| Слой | Класс |
| --- | --- |
| Персональный расчёт баллов и льгот | `AdmissionBenefitCalculator` |
| Отбор и ранжирование программ | `ProgramRecommendationPolicy` |
| Сборка плана 5×5 | `ApplicationPlanGenerator` |
| Оркестрация, API, сохранение | `RecommendationService`, `ApplicationPlanService` |
| Доступные конкурсы по льготам | `CompetitionService` |

---

## 1. Исходные данные

Программа — это набор испытаний в конкретном вузе и направлении. У каждой программы есть:

- предметы и группы предметов (`choiceGroup`);
- проходной за прошлый год и проходной текущего года;
- карта конкурсов `competitions` — по ключу `general`, `special_quota`, `separate_quota`,
  `target_quota` хранятся места, проходной, результат прошлого года и источник данных.

Поля мест и проходных по квотам в текущей демо-БД **не загружены** и равны `null`. Это
осознанное поведение: см. раздел «Ограничения данных».

---

## 2. Персональный расчёт по программе

Считает `AdmissionBenefitCalculator`. Результат содержит сумму баллов, детализацию по
испытаниям, олимпиадам и достижениям, список недостающих предметов и итоговую льготу
(в том числе БВИ).

### 2.1 Допуск (eligibility)

| Статус | Условие |
| --- | --- |
| `incomplete` | Не сданы все обязательные предметы программы. Сумма баллов при этом `null` |
| `ineligible` | Хотя бы один засчитываемый экзамен ниже минимального порога предмета |
| `eligible` | Все предметы сданы и каждый выше минимального порога |

Дополнительно программа становится `ineligible`, если по выбранному конкурсу **мест ровно 0**.
Пустое место (`null`) не считается закрытым.

Минимальные пороги берутся из справочника предметов (`Subject.minThreshold`) и одинаковы для
бота, API и подборки.

### 2.2 Выбор конкурса

`CompetitionService.available(user)` собирает список в фиксированном порядке:

1. `special_quota` — если есть льгота с таким типом квоты;
2. `separate_quota` — в том числе для участников СВО и их детей;
3. `target_quota`;
4. `general` — доступен всегда.

Если пользователь явно выбрал конкурс в настройках, он переносится в начало списка. Все
остальные остаются доступными для переключения.

**Для расчёта используется первый элемент списка** — то есть предпочтение пользователя по
умолчанию. Для квоты берётся проходной именно этой квоты. Проходной общего конкурса **никогда
не подставляется вместо проходного квоты**: при отсутствии данных по квоте `passingScore` равен
`null`, и программа честно помечается как «проходной неизвестен».

### 2.3 Сравнение с прошлогодним проходным

`scoreDifference = сумма баллов − проходной`. Считается только при `eligible` и известном
проходном, иначе `null`.

| `comparison` | Условие |
| --- | --- |
| `bvi` | Подтверждённое БВИ |
| `ineligible` | Нет допуска |
| `insufficient_data` | Проходной неизвестен |
| `near_previous` | `\|разница\| <= nearPreviousThreshold` (по умолчанию 5) |
| `above_previous` | Разница больше порога |
| `below_previous` | Разница меньше −порога |

Дополнительно для интерфейса считается `riskStatus`:

| `riskStatus` | Условие |
| --- | --- |
| `bvi` | Подтверждённое БВИ |
| `unknown` | Нет допуска или неизвестен проходной |
| `reserve` | Запас от 20 баллов |
| `real` | От 0 до 19 баллов |
| `risk` | Отрицательная разница |

Порог 20 баллов для «запаса» — продуктовое решение, а не нормативный критерий.

### 2.4 Нормализованный проходной

Чтобы сравнивать программы с разным числом экзаменов, используется относительный показатель:

```
relativePassingScore = passingScore / entranceScoreMax
entranceScoreMax     = (количество различных групп или предметов) × 100
```

Так программа с двумя экзаменами и проходным 180 (0.90) оказывается сопоставимой с программой
на три экзамена и проходным 270 (0.90), а не «хуже» из-за другой шкалы.

## 3. Рекомендации по направлению

`RecommendationService.recommend` для одного направления:

1. Загружаются **все** программы направления из всех вузов.
2. По каждой считается персональный результат.
3. `ProgramRecommendationPolicy.select` отбирает кандидатов.
4. Результат ранжируется.
5. **Первые 10** попадают в ответ.

### 3.1 Отбор

Программа попадает в список, если:

- подтверждено БВИ; **или**
- статус `eligible` и `scoreDifference` не меньше `−allowedDeficit`, либо проходной неизвестен.

`allowedDeficit` берётся из настроек пользователя. Допустимы только **0, 10, 15, 20**, по
умолчанию 15. **Верхней границы запаса нет**: программа с проходным на 40 баллов ниже вашего
результата не отсекается — она просто окажется ниже в рейтинге.

Программы без допуска и с неполными данными исключаются. БВИ проходит отбор независимо от
баллов.

### 3.2 Ранжирование

Сортировка по убыванию, по очереди:

1. `relativePassingScore` — по убыванию, программы без проходного уходят в конец;
2. `universityId`;
3. `programId`.

**БВИ не поднимает программу в рейтинге.** Приоритет за БВИ сознательно не встроен: это
решение абитуриента, и поднимать вариант автоматически значило бы навязывать выбор.

Сортировка идёт по проходному, а не по разнице с проходным. Иначе программа с проходным 190 и
результатом 195 поднималась бы выше программы с проходным 250 и результатом 300: одинаковая
дельта, но разный уровень конкуренции.

### 3.3 Ограничение количества

Лимит — **10 программ на направление**, применяется после ранжирования. Если подходящих
программ меньше, список короче. Неподходящие варианты не добавляются ради достижения числа
8–10: это была бы ложная подсказка.

Лимит применяется только к экрану рекомендаций. Автоплан и ручной подбор работают с полным
набором программ.

## 4. План 5×5

`ApplicationPlanGenerator.generate`. План — максимум **5 вузов** и **5 программ в каждом**.
Генератор ничего не сохраняет: он возвращает черновик, который пользователь подтверждает
отдельным запросом.

### 4.1 Кандидаты

Считается персональный расчёт по **всем** программам базы. В кандидат попадает программа,
если подтверждено БВИ или выполнено условие `eligible` и `scoreDifference >= −deficit`
(либо проходной неизвестен). Здесь действует тот же `deficit`, что и в настройках.

### 4.2 Направления для ранжирования

- Обычно это направления, выбранные пользователем, **в его порядке**.
- Если не выбрано ни одного, ранжирование идёт по всем направлениям, где есть кандидаты.
- **Смежные направления** — невыбранные, у которых есть хотя бы одна общая категория
  интересов с выбранными. Они участвуют только в доборе программ внутри вуза, но не влияют
  на выбор вузов.

### 4.3 Шаг 1. Рейтинг программ внутри направления

Программы ранжируются по убыванию `relativePassingScore`, без проходного — в конец, затем по
`programId`.

### 4.4 Шаг 2. Топ-3 вузов по каждому направлению

По каждому направлению для ранжирования берутся **первые три различных вуза**. Вузу
начисляются места 1, 2, 3 в каждом направлении, где он попал в топ-3. Считаются:

- `hits` — сколько раз вуз попал в топ-3;
- `sumOfPlaces` — сумма занятых мест;
- `firstPlaces` — сколько раз вуз был первым.

### 4.5 Шаг 3. Выбор вузов

В порядке приоритета берутся пять вузов:

1. **Вузы из базового плана** (режим «дополнить») — сохраняются первыми, даже если не попали
   в топ-3.
2. Остальные — по сортировке: больше `hits` → меньше `sumOfPlaces` → больше `firstPlaces` →
   `universityId`.

Логика: вуз, попавший в топ-3 сразу по нескольким направлениям, надёжнее вуза с единственным
первым местом — у него больше пересечений, меньше зависимости от одного конкурса.

### 4.6 Шаг 4. Добор вузов

Если вузов меньше пяти, доберутся следующие позиции рекомендаций: позиция 0 по всем
направлениям, затем позиция 1 и так далее, пока вузов не станет 5 или позиции не кончатся.
Повторно выбранный вуз пропускается. Такие вузы помечаются `addedAsFill = true`.

Добор нужен, чтобы план не оставался пустым там, где данных мало. Он идёт **после**
выбранных направлений, поэтому не вытесняет осмысленные варианты.

### 4.7 Шаг 5. Программы внутри вуза

Не больше пяти, **одна программа на направление**. Порядок:

1. Программы из базового плана — `retained`. Их направления считаются занятыми.
2. Выбранные пользователем направления **в порядке его выбора** — `selected_direction`. По
   направлению берётся первая подходящая программа вуза в рейтинге.
3. Смежные направления — `related_direction`.
4. Любые другие подходящие программы вуза — `auto_fill`.

Каждая программа получает объяснение, поэтому в интерфейсе видно, почему она попала в план.

### 4.8 БВИ

**Автоплан не назначает место для БВИ.** Программы с доступным БВИ попадают в план как
обычные, а список таких программ вне плана возвращается в предупреждениях: решение остаётся
за пользователем.

В режиме «дополнить» выбор БВИ из базового плана сохраняется, только если программа осталась
в плане и БВИ всё ещё доступно. Иначе выбор снимается с предупреждением.

Напоминание в интерфейсе: БВИ можно использовать только в одном вузе и на одном направлении.

### 4.9 Предупреждения

Предпросмотр возвращает список `warnings`:

- по направлению нет подходящих программ при текущем дефиците;
- БВИ доступно вне плана;
- в плане есть программы с БВИ, но место не отмечено;
- подходящих вузов меньше пяти;
- в вузе меньше пяти подходящих направлений;
- программа из плана сейчас не проходит по условиям, но оставлена.

Смысл предупреждений — показать, где план неполон, не подменяя его «более безопасным»
составом.

## 5. Ручное редактирование

Пользователь может изменить любой элемент плана вручную: добавить вуз, изменить порядок
вузов, переставить и убрать программы, отметить место для БВИ.

### 5.1 Список доступных программ

```
GET /v1/sessions/{sessionId}/application-plan/options
    ?universityId=&offset=0&limit=20
```

Возвращает программы **только по выбранным направлениям** с персональным расчётом и
`total` до пагинации. Можно фильтровать по вузу.

Здесь доступна программа с подтверждённым БВИ или со статусом `eligible` — **без фильтра по
дефициту**. Список для ручного выбора шире, чем набор кандидатов автоплана: это осознанно,
чтобы ограничение настроек не мешало добавить вуз вручную. Верхняя граница запаса не
применяется.

### 5.2 Сохранение

```
PUT /v1/sessions/{sessionId}/application-plan
{"universities": [...], "bviProgramId": "...", "expectedVersion": 3}
```

Проверки при сохранении:

- не больше 5 вузов, вузы не повторяются;
- от 1 до 5 программ в вузе, программы не повторяются;
- программа существует и относится к указанному вузу;
- **в одном вузе нельзя две программы одного направления**;
- каждая программа доступна: подтверждённое БВИ или `eligible`;
- если отмечено место для БВИ, программа есть в плане и БВИ доступно.

Оптимистичная блокировка по `expectedVersion`: при расхождении версий возвращается конфликт с
просьбой перезагрузить план. Это защищает от перезаписи изменений из другого окна.

## 6. Настройки подборки

```
GET /v1/sessions/{sessionId}/recommendation-settings
PUT /v1/sessions/{sessionId}/recommendation-settings
{"maxScoreDeficit": 15, "competitionType": "separate_quota"}
```

- `maxScoreDeficit` — только `0`, `10`, `15`, `20`.
- `competitionType` — один из доступных по льготам. Недоступное значение отклоняется.

Ответ содержит текущие значения, список допустимых дефицитов и доступные конкурсы. Значение
дефицита по умолчанию при первом расчёте — 15.

## 7. Эндпоинты

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/v1/sessions/{id}/recommendations?directionId=&offset=&limit=` | Подборка по направлению |
| `GET` | `/v1/sessions/{id}/recommendation-settings` | Настройки подборки |
| `PUT` | `/v1/sessions/{id}/recommendation-settings` | Изменить настройки |
| `GET` | `/v1/sessions/{id}/application-plan` | Сохранённый план с пересчётом |
| `POST` | `/v1/sessions/{id}/application-plan/preview` | Черновик автоплана |
| `PUT` | `/v1/sessions/{id}/application-plan` | Сохранить состав |
| `GET` | `/v1/sessions/{id}/application-plan/options` | Программы для ручного добавления |

Режимы предпросмотра:

- `generate` — генерация с нуля, `basePlan` не передаётся;
- `fill` — дополнить существующий план, `basePlan` обязателен.

Все запросы требуют `Authorization: Bearer <token>`, где `id` сессии совпадает с
аутентифицированным пользователем.

## 8. Сводка в профиле

Профиль считает две группы счётчиков.

`comparison`-группы: сколько программ с БВИ, выше проходного, около проходного, ниже
проходного и с недостатком данных.

`riskStatus`-группы: `reserveCount`, `realCount`, `riskCount` — запас, реалистичные варианты
и риск.

Совет в профиле строится по этим числам: при преобладании риска предлагается добавить программы
с запасом, при наличии запаса — держать их как страховку, а более сильные вузы ставить выше.

Сводка считается по подборкам всех выбранных направлений вместе. Лимит 10 действует в пределах
одного направления, поэтому сумма по направлениям может быть больше 10.

## 9. Ограничения данных

1. **Места и проходные по квотам не загружены.** В `V15` для квот созданы строки с `null`.
   Следствия: у квотных программ неизвестен проходной, они проходят отбор (неизвестный
   проходной не отсекается), но оказываются в самом конце рейтинга и помечаются
   `insufficient_data`. Для пользователя с лготой СВО это значит, что квотные варианты будут
   видны, но не выше общеконкурсных. До загрузки реальных цифр любые оценки квотных шансов
   были бы догадкой.
2. **Источник данных помечается как `demo`**, если по конкурсу нет отдельной записи. Это
   сделано намеренно, чтобы интерфейс не выдавал расчёт за официальные данные приёмной
   комиссии.
3. **БВИ не назначается автоматически**, а квота не подтверждается автоматически: право и
   документы проверяет приёмная комиссия. В `reasons` это указано явно.
4. **Неизвестный проходной не отсекает программу.** Сознательный компромисс: лучше показать
   вариант с пометкой о нехватке данных, чем скрыть потенциально подходящую программу.

## 11. Что стоит проверить перед релизом

- Реальные места и проходные по квотам СВО и другим льготам.
- Соответствие формулировок `reasons` юридически точным формулировкам правил приёма.
- Порог «запас от 20 баллов» — продуктовая настройка, его стоит подтвердить.
- Полный прогон интеграционных тестов: он требует Docker для Testcontainers.
