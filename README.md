# Менеджер баллов

Бот и мини-приложение в MAX для планирования поступления в вуз. Пользователь указывает баллы ЕГЭ, выбирает направления, добавляет олимпиады, индивидуальные достижения и льготы, после чего сравнивает программы и составляет план поступления.

**Домен приложения:** [runiversityadmission.ru](https://runiversityadmission.ru)

Для полного сценария и авторизации мини-приложение нужно открывать через бота MAX.

---

## Назначение решения

«Менеджер баллов» помогает абитуриенту, который хочет поступить на бюджет, собрать в одном месте данные о своём профиле поступления и превратить их в понятный план действий.

Вместо ручного сравнения правил разных вузов пользователь получает:

- единый профиль с баллами ЕГЭ;
- выбор направлений;
- учёт олимпиад, индивидуальных достижений и льгот;
- рекомендации по программам;
- объяснение расчёта конкурсного балла;
- ручной или автоматический план поступления;
- сохранение приоритетов.

Прошлогодний проходной балл используется только для сравнения и не гарантирует поступление. Итоговое решение о подаче документов и зачислении остаётся за пользователем и официальными сервисами вузов.

---

## Основной пользовательский сценарий

1. Пользователь открывает чат-бота в MAX.
2. В боте указывает баллы ЕГЭ.
3. Из бота открывает мини-приложение.
4. Выбирает интересующие направления и расставляет их по приоритету.
5. Указывает олимпиады, индивидуальные достижения и льготы.
6. Получает рекомендации по программам с расчётом и пояснением.
7. Формирует план поступления вручную или автоматически.
8. Проверяет порядок вузов и направлений.
9. Сохраняет итоговый план и при необходимости возвращается к нему позже.

---

## Возможности

- Сбор исходных данных через бота и редактирование баллов ЕГЭ в мини-приложении.
- Выбор направлений и расстановка их приоритетов.
- Учёт олимпиад, индивидуальных достижений и льгот.
- Рекомендации по программам с учётом профиля абитуриента.
- Сравнение конкурсного балла с прошлогодним проходным.
- Просмотр состава и объяснения расчёта балла.
- План «5 × 5»: до пяти вузов и до пяти различных направлений в каждом.
- Ручное составление плана.
- Автоматический подбор плана.
- Дополнение существующего плана.
- Сохранение приоритетов.

Баллы и условия поступления рассчитывает backend. Автоподбор создаёт черновик: пользователь может изменить его вручную перед сохранением.

## Логика рекомендаций и автоплана

### Рекомендации по программам

Для выбранного направления backend рассчитывает подходящие программы.

Основная логика:

1. Проверяются требования программы и допуск.
2. Учитываются олимпиады, индивидуальные достижения и льготы.
3. Варианты без допуска исключаются.
4. Доступное БВИ показывается отдельно.
5. Для остальных программ используется разница между конкурсным баллом и прошлогодним проходным.
6. Программы сортируются по результату сравнения.
7. Если исторического проходного балла нет, программа располагается после вариантов с известными данными.

Прошлогодний проходной балл не является гарантией поступления.

### Автоплан «5 × 5»

Автоплан формируется сервером из рассчитанных программ.

- Выбирается до пяти вузов.
- В каждом вузе — до пяти разных направлений.
- Сначала учитываются выбранные пользователем направления.
- Затем могут использоваться смежные направления из выбранной категории интересов.
- Если подходящих вариантов меньше, итоговый план может быть меньше 5 × 5.
- БВИ не применяется автоматически: окончательный выбор остаётся за пользователем.
- Автоплан создаётся как черновик и сохраняется отдельным действием.

## Стек и архитектура

| Компонент            | Технологии и назначение                                                |
| -------------------- | ---------------------------------------------------------------------- |
| `bot_max_backend/`   | Бот MAX и REST API: Java 21, Spring Boot, Spring Security, JPA, Flyway |
| `bot_max_frontend/`  | Мини-приложение: React, TypeScript, Vite, Redux Toolkit, MAX UI        |
| `nginx/`             | HTTPS и проксирование frontend, API и webhook                          |
| PostgreSQL           | Основные данные приложения, каталоги, профили и планы                  |
| Redis                | Состояние диалога и временные данные                                   |
| `.github/workflows/` | Автоматизация сборки и развёртывания                                   |
| `docker-compose.yml` | Серверный запуск backend, frontend, PostgreSQL, Redis и nginx          |

Упрощённая схема:

```text
MAX
│
├── чат-бот
│
└── мини-приложение
        │
        ▼
      nginx
        │
        ▼
  Spring Boot API
     │       │
     ▼       ▼
PostgreSQL  Redis
```

Расчёты выполняются на backend. Frontend получает готовые результаты API и отображает их пользователю.

Мини-приложение передаёт данные запуска MAX в API, получает JWT и использует его для защищённых запросов.

## Запуск через Docker

После настройки корневого `.env`, домена и HTTPS-сертификатов выполните из корня репозитория:

```sh
docker compose up -d --pull always
```

Команда запускает:

- backend;
- frontend;
- PostgreSQL;
- Redis;
- nginx.

Корневой `docker-compose.yml` использует готовые Docker-образы backend и frontend. Они должны быть заранее опубликованы в Docker Hub аккаунте, указанном в `DOCKER_USERNAME`.

Проверить состояние контейнеров:

```sh
docker compose ps
```

Посмотреть логи:

```sh
docker compose logs -f backend frontend nginx
```

## Переменные окружения

### Корневой `.env`

Создайте `.env` в корне проекта:

```dotenv
DOCKER_USERNAME=your-dockerhub-account

POSTGRES_DB=score_manager
POSTGRES_USER=score_manager
POSTGRES_PASSWORD=replace-with-a-strong-password

MAX_BOT_TOKEN=your-max-bot-token
MAX_WEBHOOK_SECRET=replace-with-a-random-secret

JWT_SECRET=replace-with-a-random-secret-at-least-32-characters
JWT_TTL=3600
```

Рабочие токены, пароли и ключи нельзя хранить в Git.

### Frontend `.env`

Скопируйте `bot_max_frontend/.env.example` в `bot_max_frontend/.env`.

Основные переменные:

| Переменная      | Назначение                                                                 |
| --------------- | -------------------------------------------------------------------------- |
| `VITE_API_URL`  | Адрес API. Локально: `http://localhost:8080/v1`, за общим nginx: `/api/v1` |
| `VITE_API_MODE` | `real` — реальный API, `mock` — поддерживаемые демонстрационные запросы    |
| `VITE_MAX_MODE` | `real` — запуск внутри MAX, `mock` — локальная имитация данных запуска     |

Переменные `VITE_*` встраиваются в сборку frontend. После их изменения требуется перезапуск dev-сервера или новая сборка Docker-образа.

## Локальная разработка

Нужны:

- Node.js 22;
- npm;
- JDK 21;
- Docker;
- Docker Compose.

Maven Wrapper находится в backend.

### Backend

Из корня проекта запустите PostgreSQL и Redis:

```sh
docker compose -f bot_max_backend/compose.yaml up -d
```

Перед запуском backend задайте:

```text
MAX_BOT_TOKEN
MAX_WEBHOOK_SECRET
JWT_SECRET
```

Затем:

```sh
cd bot_max_backend
./mvnw spring-boot:run
```

Для PowerShell:

```powershell
./mvnw.cmd spring-boot:run
```

Backend по умолчанию слушает порт `8080`. API использует префикс `/v1`. Миграции Flyway применяются при запуске.

### Frontend

В отдельном терминале:

```sh
cd bot_max_frontend
npm ci
```

Скопируйте `.env.example`:

```sh
cp .env.example .env
```

После настройки переменных:

```sh
npm run dev
```

Vite запускается на:

```text
http://localhost:5173
```

Для полного сценария с реальной авторизацией мини-приложение нужно открывать из бота MAX.

Если frontend и API находятся на разных origin, потребуется CORS или proxy. Текущая серверная конфигурация nginx обслуживает их через один домен.

## Развёртывание на сервере

Корневой `docker-compose.yml` использует готовые образы:

```text
${DOCKER_USERNAME}/abiturient-backend:latest
${DOCKER_USERNAME}/abiturient-frontend:latest
```

Собрать их можно из корня репозитория:

```sh
docker build -t your-dockerhub-account/abiturient-backend:latest ./bot_max_backend
docker build -t your-dockerhub-account/abiturient-frontend:latest ./bot_max_frontend
```

Отправить в Docker Hub:

```sh
docker push your-dockerhub-account/abiturient-backend:latest
docker push your-dockerhub-account/abiturient-frontend:latest
```

На сервере:

```sh
docker compose pull
docker compose up -d
```

Для своего домена измените `server_name` и пути к сертификатам в:

```text
nginx/conf.d/default.conf
```

Текущая конфигурация рассчитана на домен:

```text
runiversityadmission.ru
```

и сертификаты Let's Encrypt в:

```text
/etc/letsencrypt/live/runiversityadmission.ru/
```

Nginx направляет:

```text
/api/      → backend
/webhook/  → webhook backend
/          → frontend
```

Webhook MAX должен быть настроен на:

```text
https://<домен>/webhook/max
```

с соответствующим секретом.

## Внешние сервисы и интеграции

В текущем MVP используются:

- MAX Bot API;
- MAX mini-app / WebApp;
- Docker Hub для хранения production-образов;
- Let's Encrypt для HTTPS-сертификата.

В текущем MVP **нет прямой интеграции** с:

- Госуслугами;
- приёмными комиссиями вузов;
- государственными информационными системами;
- внешними API для автоматического обновления правил поступления.

Правила, справочники и демонстрационные данные хранятся в собственной базе приложения.

## Работа с данными

Backend хранит:

- профиль пользователя;
- баллы ЕГЭ;
- выбранные направления;
- олимпиады;
- индивидуальные достижения;
- льготы;
- рекомендации;
- план поступления и приоритеты.

PostgreSQL используется для основных данных приложения.

Redis используется для временных состояний и данных диалога.

Расчёты выполняются на backend. Frontend не рассчитывает конкурсный результат самостоятельно.

## Тестовые и демонстрационные данные

В MVP часть данных используется как демонстрационная.

Текущие ограничения данных:

- каталог не является полным каталогом всех российских вузов и программ;
- часть правил индивидуальных достижений и олимпиад требует дополнительной проверки по официальным правилам вузов;
- часть данных API помечена как демонстрационная;
- автоматический сбор и обновление правил поступления пока не реализованы.

Демонстрационные данные используются для воспроизводимой проверки MVP и не должны восприниматься как полный официальный справочник приёмной кампании.

10. Сохранить план.
11. Повторно открыть его и проверить сохранённые данные.

```sh
docker compose up -d --pull always

```

После запуска проверить:

- frontend открывается по HTTPS;
- backend отвечает через nginx;
- бот принимает сообщения;
- mini-app открывается из MAX;
- PostgreSQL и Redis доступны backend.

## Ожидаемое поведение

- После авторизации пользователь получает свою сессию.
- Выбранные данные сохраняются между экранами.
- Backend рассчитывает результаты отдельно для программ.
- Пользователь видит объяснение итогового балла.
- Прошлогодний проходной используется только как исторический ориентир.
- Автоплан создаёт черновик до 5 вузов × 5 направлений.
- Пользователь может изменить автоплан вручную.
- Итоговый план сохраняется отдельным действием.
- После повторного открытия сохранённый план восстанавливается.
- При ошибке API пользователь получает сообщение об ошибке и может повторить действие.

## Известные ограничения

- Каталог программ в MVP ограничен.
- Часть правил и данных имеет демонстрационный характер.
- Автоматическое обновление правил вузов не реализовано.
- Нет прямой интеграции с Госуслугами и информационными системами вузов.
- Прошлогодний проходной балл не гарантирует поступление.
- Рекомендации приложения не являются решением приёмной комиссии.
- Корректность правил перед реальным запуском должна дополнительно проверяться по официальным источникам.
- Для полноценной проверки авторизации mini-app нужно открывать через MAX, а не напрямую по URL.
